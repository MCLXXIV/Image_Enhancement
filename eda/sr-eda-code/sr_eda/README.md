# EDA-пайплайн для SR-проекта (90к фото недвижимости, Kaggle)

Шесть стадий, каждая пишет результат на диск и **резюмируется** — если сессия
Kaggle умерла, перезапускаете ту же ячейку, досчитается только недостающее.

```
s1_scan.py      технические метрики + деградации + phash/md5   (CPU, мультипроцесс)
s2_embed.py     CLIP-эмбеддинги всего датасета                 (GPU)
s3_iqa.py       MUSIQ/NIQE no-reference качество               (GPU, по умолчанию сэмпл 25к)
s4_semantic.py  zero-shot сцены/флаги + кластеризация + листы  (GPU/CPU)
s5_dups.py      дубликаты: md5 + phash + эмбеддинги            (CPU)
s6_report.py    графики, сегментация SR, eval-сеты, корнер-кейсы
```

Зависимости стадий: s1 — ни от чего; s2, s3 — от s1; s4, s5 — от s2;
s6 — собирает всё, что есть (выдержит отсутствие s3/s4/s5, но будет беднее).

## Как загрузить код на Kaggle

Самый удобный способ — оформить код как Kaggle Dataset:

1. На kaggle.com: **Datasets → New Dataset** → перетащите файлы `*.py`
   (или `sr_eda.zip`) → назовите, например, `sr-eda-code` → Create.
2. В ноутбуке: панель справа → **Add Input** → найдите свой `sr-eda-code`.
3. Этот же механизм используйте, чтобы между сессиями сохранять результаты:
   по окончании прогона выгрузите папку `/kaggle/working/eda` как Dataset —
   и в следующей сессии скопируете её обратно, резюмирование подхватит.

Альтернативы: ячейки `%%writefile s1_scan.py` с содержимым файлов, либо
`!git clone` из вашего репозитория.

## Ориентировочное время на 90к фото (T4, 4 CPU)

| Стадия | Время | Комментарий |
|---|---|---|
| s1 | 1.5–3 ч | CPU-bound, зависит от размеров фото |
| s2 | 15–30 мин | ViT-B/32, батч 256 |
| s3 | ~1–1.5 ч | сэмпл 25к; весь датасет ≈ ×3.5 (IQA_SAMPLE=None) |
| s4 | 15–30 мин | основное — UMAP |
| s5 | минуты | с faiss; без него до десятков минут |
| s6 | минуты | |

Всё умещается в одну сессию Kaggle с запасом.

## Что смотреть на выходе (`/kaggle/working/eda/report/`)

- `summary.md` — ключевые числа одним экраном.
- `hist_*.png`, `bar_*.png` — распределения: размеры, JPEG-качество, резкость,
  шум, блочность, MUSIQ, сцены, сегменты. Из `hist_jpeg_q_est`, `hist_noise_sigma`
  и `hist_blockiness` берутся параметры degradation pipeline для синтетических
  пар и файнтюна.
- `umap_scenes.png` — карта датасета.
- `sheets/scene_*.png`, `sheets/flag_*.png`, `sheets/cluster_*.png`,
  `sheets/segment_*.png`, `sheets/dup_group_*.png` — контактные листы.
  **Главный инструмент проверки глазами**: 15 минут пролистывания вместо
  отсматривания 90к файлов.
- `eval_real.csv` — стратифицированный реальный eval-сет (150 фото).
- `eval_hr_source.csv` — доноры эталонов для синтетических LR/HR-пар (200 фото).
- `corner_candidates.csv` + `sheets/corner_*.png` — кандидаты в корнер-кейсы
  по каждой причине (текст, вотермарки, ночь, зеркала, блочность, крошечные...).
- `eda_full.parquet` — вся объединённая таблица для своих ad-hoc запросов.

## Критические оговорки (заложены в код, но помните о них)

- Резкость (`lap_var`) считается на стандартизированном размере 1024px —
  иначе она меряет разрешение, а не резкость. Шум — наоборот, на нативном
  центр-кропе (даунскейл уничтожает шум). Блочность — только на нативном
  разрешении и осмысленна, только если фото не ресайзили после сжатия.
- Оценка JPEG-качества видит только **последнее** пересжатие.
- Zero-shot CLIP слаб на мелкий текст и мелкие лица: флаги `text`/`people`
  ловят крупное. Если по контактным листам решите, что это важно, — следующий
  шаг: отдельный детектор текста (DBNet/PaddleOCR-det) и лиц (facenet-pytorch).
- NIQE «не любит» гладкие стены (малотекстурные интерьеры) — читайте его
  только в паре с MUSIQ.
- Пороги сегментации в `config.py` — стартовые. После первого прогона
  откройте `sheets/segment_*.png`, подгоните пороги и перезапустите **только s6**
  (она пересчитывается за минуты, ничего тяжёлого не трогая).
- Не добавляйте файлы в датасет между стадиями s2–s5 (собьются индексы
  эмбеддингов); если датасет изменился — пересчитайте от s1.

## Что было протестировано

CPU-часть (s1, s5, s6, utils) прогнана end-to-end на синтетическом датасете
с известными ответами: оценка JPEG-качества сошлась с истинной (ошибка ≤0.2),
блочность монотонна по качеству, группа из 5 дубликатов (копия/ресайз/пересжатие/
осветление) собралась полностью с правильным каноником, ложные phash-пары
однотонных фото отклонены подтверждением по эмбеддингам, битые файлы ушли
в `broken`, резюмирование работает. GPU-стадии (s2–s4) проверены на синтаксис
и ревью; первые минуты их прогона на Kaggle стоит понаблюдать.
